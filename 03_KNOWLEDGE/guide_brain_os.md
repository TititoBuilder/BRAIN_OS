# Guide: Building BRAIN_OS — A Personal Operating System for Knowledge

BRAIN_OS is not a piece of software. It is a system. A set of folders, files, conventions, and tools that together create a persistent intelligence layer for everything you build. Without it, every session with an AI assistant starts from zero. With it, every session starts with full context, proven principles, and a live map of your project ecosystem.

The vault lives at C drive backslash BRAIN_OS and is tracked in a private GitHub repository at TititoBuilder slash BRAIN_OS. Every change gets committed. The git history is the audit trail for how your thinking evolved over time.

The folder structure has ten numbered directories. Each number corresponds to a category of knowledge. Zero zero holds the dashboard, a canvas file that provides a visual overview of the entire vault. Zero one holds domain documents — one file per major knowledge domain like AI Engineering, Creative Systems, and Data Science. Zero two holds two types of documents: agent nodes that document each AI agent you have built, and project nodes that document each active project. Zero five holds memory documents — running records of important facts about each system. Zero seven holds system documents including the navigation shortcuts and proven principles. Zero nine holds tools — Python scripts and utilities that are part of the BRAIN_OS workflow.

The two most critical files are Navigation Shortcuts dot md and Cristian Principles dot md. Navigation Shortcuts is 517 lines of structured reference covering every project path, every venv location, every alias, every MCP server registration command, and every tool location. It is the single source of truth. When anything moves, this file gets updated first. Cristian Principles holds the mental models that have been proven through real work. Every entry was earned by completing a task, discovering a pattern, and documenting it after the fact. No theoretical entries. No things that sound smart but have not been tested.

The knowledge management pipeline has five stages. Chat produces raw knowledge during a work session. Compile extracts the key facts, decisions, and principles from that session using session close dot py. Link connects the new knowledge to existing nodes through wiki links in Obsidian. Automate runs the relevant maintenance scripts to update graphs and sync documentation. Visualize surfaces the updated knowledge through the canvas dashboard and graph context headers.

Session close dot py is the automation backbone of the ingestion pipeline. It runs at the end of every significant session, produces a structured markdown file capturing what was built, what was decided, what was learned, and what is still pending. That file gets committed to BRAIN_OS and becomes part of the permanent record. The next session starts by loading the most recent session close file as context before any work begins.

The project nodes in zero two projects follow a consistent schema. Each node has a properties block with tags, created date, updated date, and domain. The body covers what the project is, its location on disk, its GitHub repository, its key paths, its current status, and its dependencies. Every project node links to the relevant agent nodes, domain nodes, and principle entries. The links are what make the vault a graph rather than a folder of documents.

The six projects in the ecosystem each have their own node: soccer content generator, CristianConstruction, custom agent, read-along app, Resolve MCP server, and OBS MCP server. Each also has a CLAUDE dot md file in its project root that tells Claude Code how to work in that project — what the venv path is, how to run the main script, what the key files are, and what not to touch.

The biggest mistake you can make with BRAIN_OS is treating it as an archive. An archive is something you put things into and rarely retrieve from. BRAIN_OS is active working memory. It gets read at the start of sessions, updated during sessions, and committed at the end of sessions. The velocity of your development work is directly proportional to how current and accurate the vault is. When the vault is stale, sessions are slow because time goes into re-establishing context. When the vault is current, sessions are fast because the AI already knows the system.

The discipline required is small: run session close at the end of every significant session, commit BRAIN_OS alongside the project code, and keep Navigation Shortcuts accurate. Twenty minutes of documentation discipline per session saves hours of context recovery in future sessions.
